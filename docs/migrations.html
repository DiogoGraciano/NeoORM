Histórico do schema

Mude o banco por arquivos que podem ser revisados

Models descrevem o estado desejado. Migrações registram a transição entre estados. O NeoORM compara snapshots, gera SQL específico por dialeto e detecta divergências antes de um deploy.

Fluxo recomendado

  1. Altere um ou mais models.
  2. Rode generate:types e revise o código gerado.
  3. Gere a migração, revise o SQL, o journal e o snapshot.
  4. Aplique localmente com migration:up.
  5. Rode db:check --strict e comite todos os arquivos.
vendor/bin/neoorm generate:types
vendor/bin/neoorm migration:generate --name=add_slug
vendor/bin/neoorm migration:up
vendor/bin/neoorm db:check --strict

migration:generate não conecta ao banco: ele compara arquivos JSON e produz SQL. Isso permite revisar a alteração e executá-la no CI sem serviço de banco.

O que entra no repositório

Migrations/
  mysql/
    0000_initial.sql
    0001_add_slug.sql
    journal.json
    meta/0000_snapshot.json
    meta/0001_snapshot.json
  pgsql/
    ... mesmo layout, SQL próprio do dialeto

Todos esses arquivos são código-fonte. O snapshot é a entrada do differ; sem ele, dois desenvolvedores podem gerar a mesma próxima posição com conteúdos diferentes. Um diretório por dialeto é necessário porque engine, collation e parte do DDL não existem nos dois bancos.

Gerar e renomear

# Gera SQL, journal e snapshot. Recusa operações destrutivas por padrão.
vendor/bin/neoorm migration:generate --name=add_slug

# Cria um marco sem diferenças de schema.
vendor/bin/neoorm migration:generate --name=backfill_status --empty

# Informa um rename para preservar dados.
vendor/bin/neoorm migration:generate --name=rename_email \
  --rename=users.email_address:email

# Prévia sem escrever arquivos.
vendor/bin/neoorm migration:generate --name=preview --dry-run

--rename pode ser repetido. Para coluna, use tabela.antiga:nova; para tabela, use antiga:nova. Revise todo SQL de operações destrutivas e use --allow-destructive somente quando a perda de dados for deliberada.

Aplicar e auditar

vendor/bin/neoorm migration:up
vendor/bin/neoorm migration:up --to=add_slug
vendor/bin/neoorm migration:up --step=1
vendor/bin/neoorm migration:up --dry-run

vendor/bin/neoorm migration:status
vendor/bin/neoorm db:check
vendor/bin/neoorm db:check --strict

migration:up aceita nenhuma, uma ou várias migrações pendentes. Se não houver pendências, sai com sucesso — comportamento importante em deploys repetidos. migration:status retorna código 1 em caso de arquivo ausente, migração alterada ou aplicação interrompida. db:check compara models, snapshot e banco; --strict também reprova tabelas no banco que nenhum model declara.

Atalhos de desenvolvimento

# Converge o banco direto com os models; não cria arquivo de histórico.
vendor/bin/neoorm db:push
vendor/bin/neoorm db:push --dry-run

# Lê o schema atual; sem --write-to, imprime JSON em stdout.
vendor/bin/neoorm db:pull --write-to=database-snapshot.json
vendor/bin/neoorm db:pull --only-declared

# Destrói e recria o banco configurado; desenvolvimento apenas.
vendor/bin/neoorm db:reset --force --seed
vendor/bin/neoorm db:reset --confirm=nome_do_banco

db:push não é uma estratégia de produção. Ele é útil no ciclo local, quando o model muda rapidamente, mas não cria artefato para revisão nem para reproduzir outro ambiente. Em ENVIRONMENT=prod, db:push e db:reset são recusados.

Atomicidade por banco

BancoGarantiaSe uma migration falhar
PostgreSQLDDL transacionalO DDL e seu registro fazem commit juntos, ou nada é aplicado.
MySQLDDL com commit implícitoO runner grava applied_index após cada statement; a próxima execução retoma no ponto correto.

Essa diferença é intencionalmente visível. O NeoORM não finge que DDL do MySQL pode ser atômico; ele torna uma falha diagnosticável e retomável.

Sem down

Não há migração automática de rollback. Um DROP COLUMN revertido recria a coluna, mas não os dados perdidos; chamar isso de reversão é enganar o operador. Em desenvolvimento, use db:reset. Em produção, crie uma migração corretiva para frente.

CI mínimo

vendor/bin/neoorm generate:types --check
vendor/bin/neoorm migration:status
vendor/bin/neoorm db:check --strict

Inclua um banco de teste no pipeline para os dois últimos comandos. Para testar a biblioteca, o repositório disponibiliza composer test, composer test:unit, composer test:types e suites específicas dos dois dialetos.
